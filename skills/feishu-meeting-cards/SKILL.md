# 会议转写 → 报告 + 任务卡片 + 推送

## 何时用

- 用户甩来一条飞书**会议文字记录**链接（`.../docx/xxx`），要"报告 / 任务卡片 / 建议如何推进"。
- 周会、项目组会、客户沟通会后需要落地成行动项。
- 最后一步常是"发送我的飞书个人"→ 云文档 + 私聊推送。

## 步骤

### 0. 写前对源（★ 2026-10-10 新增，动笔之前先过）

> 起因：客户A管理层卡片 v1→v10 改 9 次。**问题不在"写"，在"核"排在了"写"后面。**

- **证据齐了才动笔**：先把要写的**每条结论 → 出处 → 置信度**列成三列表给用户过，过了再写稿。错误拦在核对表阶段，不在第 10 版。
- **证据分级**：**A 一手**（妙记**转写原文** / 线上表实读 / 群消息原文 / 私聊原文）= 唯一可作事实；**B 二手**（妙记 **AI 摘要** / 上一版稿件 / 转述）须回 A 级复核；**C 推断**（我判的）**不进对客物**。
- ★**三类高频坑，写前先自查**：
  1. **涉时间节点必回转写原文**——相对时间（今天/明天/下周）在 AI 摘要里会被吞或错位 → 日期差一天。
  2. **禁顺抄上一版稿件**——旧稿条目在前提变了之后就是毒药，**抄一条核一条**。
  3. **输入若是"汇总"（跨多场会议/跨周）**，别只读一份 docx：**必拉数据仓群消息 + 私聊层**（`hub.db` 不含私聊，须 `im +messages-search --chat-type p2p`）；漏私聊会把"已转交他人"的活错挂在自己名下。
- **决策人按职责挂**：业务范围→业务方；选型/合规→法务/内控；技术路线→项目侧。**不默认挂项目牵头人。**

### 1. 取转写全文
```bash
lark-cli docs +fetch --doc "<url或token>" --doc-format markdown --as user
```
- 转写格式：每段 = 说话人 + 时间戳 + 话语；`<cite uid-ref="u1">` 配合 `reference_map` 给出 open_id（`u1/u2/u3` 映射）。
- 文末 `_notice` 里的 `document.tips` 会提示"这是逐字稿"。
- 智能纪要通常是另一个 docx，链接出现在正文首部。

### 2. 实读线上实施表，把会议产出对到任务编号
```bash
lark-cli base +record-list --base-token <base> --table-id <tbl> --format ndjson --output ./tasks.ndjson --overwrite --as user
```
- ⚠️ **没有 `--page-all`**（那是别的子命令的），record-list 用 `--limit`（ndjson 默认 2000）。
- 用 python 打印紧凑清单：任务编号 / 状态 / 主题 / 客户方任务+负责人 / 我方任务+负责人 / 最新进展前 70 字。
- 会议里出现的具体人名 → 反查任务里对应条目（如"客户来访登记"→ T64），报告中带上编号才可执行。

### 3. 产出报告（写本地 md）

固定骨架：

1. **一句话结论**（3–4 个信号）
2. **决议台账**：`# / 事项 / 结论 / 客户方责任人 / 我方责任人 / 时限`——★**承诺必须点名到人**，禁默认"我方=某个人"
3. **任务卡片**：我方 / 客户方 / 我方非本人 三组，卡片字段 = `卡号 / 任务 / 交付物或完成口径 / 关联编号 / 优先级`
4. **推进建议**：P0 今晚 / P1 节后（或次日）/ P2 一周内 + "推进要点（避免踩坑）"
5. **会上未闭环**：卡在哪、找谁
6. **可发送文案草稿**：★标"待确认，未发送"
7. **线上表待更新清单**：★**只列不写**（写线上须用户明确授权）

### 4. 导入云文档
```bash
cd <临时目录>   # ★ 必须先切到临时目录
lark-cli docs +create --title "<标题>" --doc-format markdown \
  --content @./report.md --parent-position my_library --as user
```
- ⚠️ **`@file` 只接受 cwd 相对路径**；给绝对路径报 `unsafe file path`。把文件复制到临时目录再 `cd` 过去。
- 标题若含 `【】·` 等中文可正常用。

### 5. 回读校验 + 修 markdown 解析坑
```bash
lark-cli docs +fetch --doc <doc_id> --doc-format markdown --as user --jq '.data.document.content'
```
**★最大的坑：表格 cell 内的加粗会被吞。**
- 现象：`①纷享销客+金蝶**各自**接飞书；…**我方建议飞书为中枢**（` 回读变成 `①纷享销客+金蝶**各自接飞书…我方建议飞书为中枢**（`——`**` 配对错位、内容被吃进加粗。
- 规律：**加粗结束符 `**` 后紧跟中文字符**时不可靠（`**各自**接`、`**逻辑**不`）；后跟全角标点/空格则通常安全。
- **对策：表格行内一律不用 `**`。** 写前跑一遍：
```python
for l in src.splitlines():
    if l.lstrip().startswith('|'):
        l = l.replace('**', '')
```
- 修订后覆盖（仅限自己刚创建、无其他内容的文档）：
```bash
lark-cli docs +update --doc <doc_id> --command overwrite --doc-format markdown --content @./fixed.md --as user
```
- 覆盖后**再回读一次**确认表格列未错位。

### 6. 推送我的飞书私聊

★**默认用「消息卡片」，不是 markdown / 不是云文档链接**（用户 2026-09-30 明确口径：「消息卡片的形式」「不要文档」）。

```bash
cd <临时目录>
lark-cli im +messages-send --user-id <OPEN_ID> \
  --msg-type interactive --content "$(cat card.json)" \
  --idempotency-key <key> --as user
```
- ⚠️ **`--content` 不吃 `@file`**（`@./card.json` 报 `--content is not valid JSON`）；只有 `docs +create--content` 支持 `@`。必须 `"$(cat card.json)"` 内联（文件放临时目录再 cd 过去）。

卡片结构（1.0，`config.wide_screen_mode` + `header.template` + `elements[]`）：

- `header.template`：orange / blue / red…；`header.title` = `{"tag":"plain_text","content":"【项目名】日期 · 主题"}`。
- 分区：依次放 **决议 / 今晚必须收口 / 我方任务卡（🔴🟠🟡 分级）/ 客户方待办 / 未闭环**，区与区之间用 `{"tag":"hr"}`。
- 文本块用 `{"tag":"div","text":{"tag":"lark_md","content":"..."}}`；**行内 `**加粗**` 后紧跟中文在卡片里是安全的**（被吞只发生在 markdown *文档导入*的表格 cell 里）。
- ⚠️ **卡片 2.0 的 `table` 组件在飞书消息卡片里不渲染**，用 `div` + 换行代替；`note` 标签也不支持。
- ⚠️ 卡片里**不放云文档链接**（用户明确不要）；纯卡片内容自足。

其他要点：
- `--user-id` 发给自己返回 p2p `chat_id`（该账号为 `<CHAT_ID>` = 飞书里的「**我**」）。★该会话**无未读红点**，用户可能"看不到" → 推送后**主动说明位置**。
- ★**要「有红点提醒」就改用应用身份发**（实测可行）：
```bash
lark-cli im +messages-send --user-id <OPEN_ID> \
  --msg-type interactive --content "$(cat card.json)" \
  --idempotency-key <key> --as bot
```
  - bot 是 app `<APP_ID>` = **「Claw」**；落到与 Claw 的 p2p `<CHAT_ID>`，**有未读提醒**，卡片正常渲染。
  - 换身份重发要**换 idempotency-key**（key 相同会被判重复）。
- `--idempotency-key` 防重复发送（换形式重发要换 key）。
- 回读校验：`lark-cli im +messages-mget --message-ids om_xxx --as user`，看 `msg_type=interactive` 与 `sender.name`。
  - ★回读里若看到 `<card title="...">…</card>`，那是 lark-cli 的**反解渲染**，不是原始 content（post 类消息同样被反解成 markdown）——**卡片本身没坏**，不要据此以为发送失败。

## 卡片美化模板（1.0，实测可渲染）

★**排序铁律：行动在前、背景在后**（用户 2026-09-30 判过一轮"不够清晰"）。区块顺序固定为：
`概览数字条 → ① 我今晚要做 → ② 节后要做 → ③ 要客户动 → ④ 卡点找谁 → 背景决议 → 人员一行`。
- 用 `①②③` 圈号做小节前缀，比 `1.2.3.` 更容易跳读。
- **背景/决议放最后**，别放前面占屏；人员速查**降到一行**（两列网格太占版面，只在"人手分工"是主题时才用）。
- 每条行动写成 `**动词短句**` + 换行缩进 `　` 补"给谁/完成口径"，避免长句换行糊成一片。

版式自上而下：
1. **概览数字条** —— `column_set` 4 栏（`background_style: "grey"` → 灰底小块，观感最接近官方模板）：
```json
{"tag":"column_set","flex_mode":"none","background_style":"grey","columns":[
  {"tag":"column","width":"weighted","weight":1,"elements":[{"tag":"div","text":{"tag":"lark_md","content":"**4**\n决议"}}]},
  {"tag":"column","width":"weighted","weight":1,"elements":[{"tag":"div","text":{"tag":"lark_md","content":"**11**\n我方任务"}}]}
]}
```
2. `hr`
3. **人员速查** —— `div.fields`，每项 `{"is_short":true,"text":{"tag":"lark_md","content":"**姓名 · 侧**\n角色"}}` → 自动排成两列网格；最后一条 `is_short:false` 占整行。
4. `hr` + `div` 小节标题（`**四条决议（点名到人）**`）
5. **决议** —— `div.fields`，4 条各 `is_short:false`：`**1 · 事项**\n结论｜责任人`
6. `hr` + **任务卡** —— 单个 `div`，按 🔴 P0 / 🟠 P1 / 🟡 P2 三段分组，同段落多条用 `　·　` 并排省行
7. `hr` + 客户方待办（`· **人** → 事`）+ 未闭环找谁（`· 事 → **人**`）

要点：
- 概览块 + fields 网格是"美化"的性价比最高两招；**不需要**卡片 2.0（2.0 的 `table`/`note` 不渲染，且 1.0 已够）。
- 只允许**颜色 emoji**（🔴🟠🟡🟢），别加 📌/✅ 这类装饰 emoji。
- 长卡片（>3KB content）没问题，实测 3.3KB 正常渲染。

## 对外版（发客户群）

内部版 ≠ 对外版。要发客户群/客户可见处时，**先跑 `feishu-outbound-gate` 门禁**，再按白名单改写：

| 删/改 | 内部版里长什么样 |
|---|---|
| 删整块 | 我方的行动清单（含 "落表 / 发某人 / 回原厂" 这类内部动作）、概览数字条、人员速查、"卡点"块 |
| 中性化措辞 | 「卡点 → 找谁」→「待确认事项」；「缺人 → 客户财务同事出面邀（已邀 3–4 次未成）」→「需补充人力，建议由分管领导牵头协调」 |
| 删内部观察 | 「客户IT负责人病假中」「最大工期风险」「X 邀 Y 数次未成」——**不能把客户内部的人和状态写进对客材料** |
| 去内部人名 | 我方实名（本人 / 团队负责人 / CSM负责人）→ 一律写「我方」；客户侧**优先用部门/角色**（销售支持部 / 信息部门），要点名到人须用户逐条确认 |
| 改标题视角 | 「行动清单（节前收口）」→「纪要要点与后续安排」；表头色 orange → blue（内部橙 / 对外蓝，便于一眼区分） |

**保留不改**：已确认的硬节点（如 10/8）、客户方既有的分工对象、方案建议口径（"建议以飞书为中枢，待贵司决策"）。
**新增措辞**：原文里没有的承诺/日期一律不加；末行加「如有出入请指出，我方即时修订」而非内部口吻。

⚠️ 外发**必须**有明确授权（群名 + 「发」）；「我要发的」只授权出稿，不授权发出去。

### 对外版 2.0：按事项重组（用户 2026-09-30 判「要更清晰」后的定版）

对外版 v1 沿用内部版的分块（要点 / 待确认 / 我方安排 / 贵司待办）→ 对客场景的硬伤是**同一事项被切进 3–4 个段落**（"集成"同时出现在要点②、待确认③、我方安排①、贵司待办⑤），客户读完仍不知"谁做、何时做"。

2.0 改**按事项重组**，固定 4 块：

```
一、事项与分工     ← 每条 = 加粗事项名 + 「我方：…」/「贵司：…」两行
二、待贵司决策     ← 只放"要客户拍板"的（路线 / 人力 / 费用）
三、时间节点       ← 只写已确认的硬节点
四、待安排         ← 待约时间的（专项对齐 / 范围确认）
```

要点：
- 每条事项**固定两行对照**「我方：」「贵司：」，替代散文——这是清晰度的主要来源。
- **同一事项只出现一次**；决策项去重合并。
- 卡片里用 `**N．事项名**\n我方：…\n贵司：…`，**不要用 `div.fields` 做两列**（fields 在窄屏会挤成一坨，且长文本换行不可控）。
- 概览条压到 **3 栏**：`事项 N / 待决策 N / 硬节点日期`。
- 「贵司：—」这种空值**保留不删**（保持两行节奏一致，扫读更快）。

### 对外版 3.0：内容具体化（用户 2026-09-30 判「内容太笼统」后的定版）

结构对了仍会"不清晰"，因为**用词是空话**。对客文本禁用笼统动词，按三条规则改写：

| 规则 | 笼统（禁） | 具体（用） |
|---|---|---|
| ① **名词要具体** | 「提供方案与技术支持」「集成资料清单」 | 写**材料名 + 所含内容物**：「提交《集成方案对比》（飞书中枢 / CRM 中枢，含数据流向、冗余、导出方式、费用、工期）」 |
| ② **动词可核对** | 支持 / 推进 / 关注 / 加强 / 配合好 | 确定 / 安排 / 整理 / 提交 / 确认 —— 完成后能被外部核对 |
| ③ **时间落到日期** | 尽快 / 后续 / 节后 / 近期 | 「今日」「10/8」——客户能对着日历等 |

配套两条：
- **拆执行 vs 拍板**：事项块的「贵司」行只写**执行动作**（安排对接、整理口径），决策块只写**要拍板的**（路线 / 接口 / 费用）。不拆就会两处重复（这是"不清晰"的常见隐藏成因）。
- ⚠️ **具体化会引入承诺**：把内部排期（如 P1 节后首日交材料）写进对客材料 = **对客承诺**。做法：照写具体日期，但在文件里**单列「发前必核：新增承诺 N 条」**让用户确认能否兑现，或退回「节后首周」。

★**教训（诊断顺序）**：用户说"不清晰"时，按序排查 **① 内容笼统 → ② 信息重复 → ③ 排序（行动在后）→ ④ 版式**。**连错两次就直接出选项让用户点**（`AskUserQuestion`），不要第三次盲改——2026-09-30 客户A对客版即连错两轮后才问到真因。

## 管理层版（向上汇报）

**同一份会议材料有 4 种受众版本，别混用**：

| 版本 | 给谁 | 人称 | 关键差异 |
|---|---|---|---|
| 内部版 | 自己 | 我方实名 | 只写"我"要做的，带 JC 编号、卡点、内部观察 |
| 对客版 | 客户群 | 「我方」/ 部门角色 | **删**决策块与内部观察，通篇中性、可公开 |
| **管理层版** | 客户管理层 / 上级 | **点名到人** | **突出**「要谁拍板 + 何时 + 不决的影响」，任务清单降为附注 |
| 卡片 | 任意上述 | 同上 | 消息卡片形式，无云文档链接 |

**管理层版结构（固定）**：
```
概览数字条（待决策 N / 硬节点日期 / 任务完成 N-M）
→ 整体状态（一句话）
→ 任务总览（总数 + 三态分布）
→ 本周关键进展（到人、到日）
→ 需管理层决策 N 项  ← 全文重心
→ 风险与依赖（到人）
→ 下一周期计划（到人、到时间）
→ 附：口径说明
```

要点：
- **管理层只看三样**：卡在哪、要谁拍板、什么时候。任务明细是附注，不要放主体。
- **「需管理层决策」条必须四要素齐全**：决策事项 / 决策人 / 需要时间 / **未决策的影响**（最后一项最容易被漏，也最能推动拍板）。
- ★**决策人按职责挂，不默认挂项目牵头人**（2026-10-10 实证：两条决策项全挂"客户接口人"，实为业务范围归**客户方接口人（营销中心）**、选型合规归**陈娜（法务）/曾雪敏（内控）**）。业务范围→业务方；选型/合规→法务/内控；技术路线→项目侧。
- ★**只陈述事实，不写判定**：**不写「定了 / 没定 / 尚待验证 / 已对齐」**——把过程发言当结论等于替客户下结论。用户明确口径（2026-10-10）：**"只写有这事情"**。
- ★**已发出的条目要删**：用户说某条"已发过了"，整条移除并自检关键词 0 命中（2026-10-10 实证）。
- **到人写法**：`事项 —— 责任人，时间`，责任人与时间**加粗**（如 `集成中枢路线 —— 客户接口人，10/8 前`）。
- 表头色：内部 orange / 对客 blue / **管理层 indigo** —— 一眼区分，避免发错版本。
- ★**发布边界**：即使点名到人，仍守对外门禁——不写人员状态（病假）、不写内部排期编号、不写客户内部人事协调过程；客户高管用尊称。**管理层版通常是"可外发"版本**，按对客标准审一遍再发。
- ★**"给我发一下" ≠ 授权推送给管理层**：那只授权发到用户自己的会话。要真正推给管理层，须问清**发往哪个群/哪个对象**。

### 固定模板 + 生成脚本（2026-09-30 起，管理层周报默认走这个）

用户已定版：「以后用这个形式推」。**别再手写卡片 JSON**，用生成器：

```
<WORKSPACE>/工具/feishu-card-templates/
├── make_weekly_card.py      # 数据 JSON -> 飞书卡片 JSON（可 --send 直推）
├── example_input.json       # 输入样例（客户A 9/24–9/30 实例）
└── README.md
```

```bash
python3 make_weekly_card.py --input <数据.json> --out <卡片.json>
python3 make_weekly_card.py --input <数据.json> --send --to <ou_/oc_> --as bot --key <幂等键>
```
- `--to` 以 `oc_` 开头自动走 `--chat-id`，否则 `--user-id`。
- **数据与版式分离**：每周只改数据 JSON（`项目资料/<日期>_项目周报_数据源.json`），版式由脚本产出，保证形式不漂移。
- 脚本负责的固定版式：概览条 → 一 整体状态 → 二 任务总览 → 三 进展 → **四 需管理层决策** → 五 风险 → 六 下一周期 → 页脚；日期/时间自动加粗，`text`/`item`/`owner` 内可自行写 `**`。
- ★**板式一致性校验**：新写的卡片要与脚本产物 diff 一遍（比对 `elements` 里各 `div.text.content`），避免手工版与模板版两套形式并存。

## 注意事项

- **只读红线**：写线上表、发群消息、发客户私聊，**都要用户明确授权**（"发送/提交/写进去"才算，go/好/嗯不算）。默认只出草稿 + 待更新清单。
- **对外物最小改动**：给客户看的版本，只做"对外可见性"必要替换，不顺手改负责人/分工。
- **写前先对源**（见 §步骤 0）：不拿 AI 摘要当事实源、不顺抄旧稿、涉时间节点回转写原文、决策人按职责挂。
- **出手前跑门禁**：给管理层/客户的版本，**自跑 `feishu-outbound-gate` 六道检查**，不等用户喊（2026-10-10 实证：手上明明有门禁却跳过，导致 9 次返工）。
- **改完必自检**：重新生成卡片后，用脚本统计关键词命中数（如 `错词 → 0`、`客户方接口人 → 3`）自证改干净；**多版本并存时明确声明"以 vN 为准、vX 作废"**。
- 本地交付物与线上文档若因去加粗而不一致，**同步回本地**，避免两份漂移。
- 完成后把关键坑（新踩到的）补进本 skill。
