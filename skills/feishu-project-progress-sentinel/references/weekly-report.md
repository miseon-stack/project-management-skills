# 项目周报模板（三项目 · ≤500 字）

**用户口径（2026-09-19）**：「这个相当于周报的形式 —— 项目周报，然后压缩在 500 字内」。

要点：把巡检结果**收敛成一份能直接看、直接转发的项目周报**，而不是把巡检报告搬出去。周报是**汇报物**，巡检报告是**证据物**，两者分开。

---

## 一、固定结构（四块，顺序不可变）

```
📊 项目周报 · <起始日> → <结束日>          ← 标题（含日期区间）

🏭 <项目A> · <一句话定位>
• 本周关键事件（会议/决策，带日期）
• 表内数字（总条数 + 状态分布 / 子项目完成度）
• ⚠️ 卡点或硬节点

🤖 <项目B> · <一句话定位>       ← 同上三条
🔌 <项目C> · <一句话定位>       ← 同上三条

🎯 下周重点
1. <项目A>：<动作> + <目标日>
2. <项目B>：…
3. <项目C>：…

> 内部周报 · 数据截至 <日期>
```

- **每项目固定 3 条**，不多不少：一条事件、一条数字、一条风险/节点。想让某项目多说，改的是「下周重点」，不是往块里加行。
- **顺序**：按当周信息量/紧要度排（近期惯例：客户C → 客户B → 客户A，或把最紧的（客户B 9/24）放前）。
- **数字只放可信的**：总条数 + 已完成/进行中/未开始；子项目只列已完结或异常的（如 `T21、T44 已完结`；异常口径如 `T20 父行已完成但 3/6` 才展开）。
- **⚠️ 行必须是可行动的**：卡点写「谁/什么原因/影响哪个节点」，不写「进度待跟进」。

## 二、硬约束

| 约束 | 口径 |
|---|---|
| 字数 | **可见字符 ≤500**（含标点、含标题；按 2026-09-19 定稿实测 447 为安全基准） |
| 密度 | 一条一行，一行一个信息点；**禁止长段落**，不写解释性从句 |
| 语气 | 内部周报：可用「卡点/逾期/待对齐」，但**不带审计措辞**（"误报""初判"），不带商务/付款/内部投入量 |
| 事实 | 只写取数当日的线上表与会议结论；不确定的写「待对齐」，不写结论 |
| ★称谓 | **一律写任务名，不出现任务编号**（`T14`/`T21` 这类）—— 用户 2026-09-19 明示「不能说 T14，要说名字」。周报会被转给不认编号的读者；编号只在表内 / 内部巡检卡片里用于追踪。名字太长时用**可识别的简称**（如「发票流程样板搭建（回款状态流转）」→「发票流程样板搭建」、「资料自助获取能力配置」→「自助获取」），但**不能用编号代替名字** |

## 三、数据来源（不重新采集）

1. `巡检报告-<项目>-<日期>.md` 的 **概览段 + P0/P1 标题**（数字、逾期项、负责人）。
2. 会前会后的**妙记/会议结论**（本周关键事件）。
3. 长期记忆里的**硬节点**（客户B一期 9/24、发布会 10/16；客户A 10/8；客户C 2 单试跑）。
4. 需要"当周"口径时，用 `snapshot_table.py` + `diff_messages.py` 的两日 diff 结果。

## 四、产出与自检

```bash
cd "<工作区>/.workbuddy/巡检"
# ① markdown 版（给人看、可入归档）
#    周报-<日期>.md
# ② 卡片版（发给本人）
#    cards/card-周报-<日期>.json   ← 结构：{"msg_type":"interactive","card":{...}}
# 改版迭代时：旧版先另存 周报-<日期>-v1.md / cards/card-周报-<日期>-v1.json

# ③ 字数自检（必跑，超 500 就删字）
python3 -c "
import json,re
c=json.load(open('cards/card-周报-<日期>.json',encoding='utf-8'))['card']
t='\n'.join(e['text']['content'] for e in c['elements'] if e['tag']=='div')
print('可见字符:', len(re.sub(r'\s','',re.sub(r'[*•#]','',t))))
"
```

## 五、推送

**「推送给我 / 发我看看」= bot 私信本人**，不是发群、不是 webhook：

```bash
cd "<工作区>/.workbuddy/巡检"
CARD=$(python3 -c "import json;print(json.dumps(json.load(open('cards/card-周报-<日期>.json',encoding='utf-8'))['card'],ensure_ascii=False))")
lark-cli im +messages-send --user-id <OPEN_ID> --as bot \
  --msg-type interactive --content "$CARD" \
  --idempotency-key weekly-report-<YYYYMMDD>          # ★必须带，防重；改版重发要换 key（-v2/-v3）
```

- 传的是 **card 本体**（`{config,header,elements}`），**不要包 `msg_type` 外壳**；webhook 通道才需要 `{msg_type,card}` 包装。
- 先 `--dry-run` 看一遍 body 再发。
- **要发项目群 / 正式 webhook 必须单独授权**；测试 webhook（只有本人可见）可作留痕副本。

## 六、踩过的坑

1. **字数按「正文」算会超**：卡片还带 note（数据源）+ 标题，一并计入，按 447 留余量。
2. **改版重发沿用旧 idempotency-key → 被静默去重**，以为发了其实没发（本次 v2 已换 key）。
3. **别把巡检报告的 P0 明细整段搬进周报**：周报只留「几条逾期 + 卡在哪个环节 + 谁」，明细留在报告/项目表里。
4. **项目侧口径异常要标注但不要下结论**（如客户B T20 父行"已完成"但子任务 3/6）→ 写成「表内口径待对齐」，改写权归用户。
5. **不要写任务编号**（2026-09-19 用户纠正）：「⚠️ T14 发票样板是验收前置」❌ → 「⚠️「发票流程样板搭建」是验收前置」✅。定稿前必跑残留自检：`python3 -c "import json,re; c=json.load(open('cards/card-周报-<日期>.json',encoding='utf-8'))['card']; t=''.join(e['text']['content'] for e in c['elements'] if e['tag']=='div'); print(re.findall(r'T\d{2}',t))"`（应输出 `[]`）。
6. **客户A「客户新增诉求」条数**：原始信号 8 条 = 真需求 5 + 重复 1 + 非需求 2，**对外只写 6 条**（口径见项目记忆）—— 报数字前先按证据去重、去掉「帮我同步给某人」这类非需求发言。
